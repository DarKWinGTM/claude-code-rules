## Target and Scope

Keep the ordered 19 body-sufficient Main Runtime Rules while reducing repeated decision meaning within and across owners. Source development belongs exclusively to the selected Active Project Root; the user profile is a downstream install target. Existing modified/untracked source state is preserved rather than reset or replaced from a release.

One mechanism has one complete canonical runtime owner. Consumers retain activation, local consequences, necessary synchronized literals/order, and handoff—not another full policy. Runtime roots must remain independently useful behavior contracts rather than metadata/pointers. Preserve role boundaries, force/approval semantics, registries, exception branches, representation contracts, and evidence levels; reducing characters alone does not prove semantic preservation.

Global and project CLAUDE.md, reasoning frameworks, output styles, shared-board rules, unrelated plugin state, and Product behavior remain outside the compaction target. Token UI reports are observations for their capture scope; Unicode characters, UTF-8 bytes, and provider tokens are separate measures.

## Proportionate Reasoning

Start from the selected outcome and checked requirements. Separate facts, assumptions, user choices, hard requirements, and optional precautions. Choose the simplest complete path. An observation of risk does not automatically authorize an extra guard, state, queue, review, task, fallback, or architecture. Optional mitigation needs a concrete in-scope failure/benefit that justifies complexity, cost, delay, and side effects; required correctness/security and applicable approval boundaries remain binding.

Investigate decision-changing factual uncertainty using the smallest discriminating check. Consult the user for unresolved material preference, acceptance, scope, authority, cost, or approval trade-offs—not every safe microstep. Stop reasoning when the decision is supported and close at the selected proof gate; reopen only for new decision-changing evidence, correction, or failed checks.

## Additional Trial Disposition

Loaded/injected instruction availability does not prove use, effect, or promotion value. Original JSONL witnesses distinguish observed concerns, independent behavior incidents, rule application, outcomes, and causal benefit. Duplicate source doctrine is not an ineffective concept; it is unnecessary parallel runtime text. Missing evaluation is not a failed test.

The user selected removal of thirteen specific redundant/unsupported additional files after matching Main verification and exact byte/hash/mode rollback preservation. Scope and per-file rationale remain in the [active execution phase](../../phase/phase-073-16-proportionate-runtime-compaction-and-additional-convergence.md), not this target-state body. No shared/global/other-owner files are included.

Only a demonstrated same-outcome, same-proof-layer status conflict warrants a minimal reconciliation addition in the task owner. If integrated and verified, its full trial copy is retired; if original evidence remains unresolved, retain only a distinct, nonduplicated trial hypothesis at the current additional path. Separately scoped local trial payloads may live under `support/runtime-trials/memory-context-intelligence/` for their exact additional destinations. They are not part of the Main publication or nineteen-Rule installation; their local deployment provenance does not assert that this release distributes a support package. They remain outside Main doctrine, whole-plugin installation and history authority.

Analysis candidate entailment belongs to the source plugin's generation/binding boundary before ranking and presentation. A source-local fix preserves valid candidates, narrows supported parts, demotes context-only records, rejects unrelated claims, allows fewer/no topics, and avoids falsely observed before/after examples. It must not be repaired by duplicating a global Main Rule. Retain the unique plugin trial only until matching source tests prove absorption; plugin installation/live command proof is distinct from local source tests.

## Verification and Installation Boundaries

Map material old clauses to new owner, trigger, action, exception, and proof. Check focused decisions for safe continuation, exact approval, unavailable selected proof versus optional proof, same-goal status disagreements, source-first preservation, fresh correction, proportionate tests/helpers, and evidence limits. Verify body/metadata/version/reference integrity and unchanged ordered install arrays.

Run existing shell/PowerShell fixture checks before root installation. Install only from the checked source set, verify exact bytes/modes/metadata/bodies, and preserve unrelated runtime state. Apply approved additional deletion only after Main parity; rollback material stays outside rule discovery and is never an automatic fallback. Retained trials remain at their selected path without repeating Main doctrine.

Measure Main wording reduction separately from additional removal and integration growth. An estimated reduction is not installed savings; character reduction is not exact token reduction or proof the earlier 150k-character warning is resolved.

Source and installed verification may close their bounded gates. The maintainer release wave remains unpublished until separately authorized commit/push/tag/release gates pass; no release or full-project convergence claim follows from payload parity alone.
